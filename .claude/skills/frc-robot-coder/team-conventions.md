## Conventions (follow these)

1. **Constants**: nested `public static class` per subsystem inside `src\main\java\frc\robot\Constants\SubsystemConstants.java`. Package is `frc.robot.Constants` — **capitalized, nonstandard**; keep it, don't "fix" it. Import style: `import frc.robot.Constants.SubsystemConstants.ShooterSubsystemConstants;`. IDs and gear ratios are `final`; tunables are non-final `public static double` — that includes PID/FF gains **and** shooter setpoints/limits (`SHOOTER_HIGH_SPEED`, `MAX_ANGLE`, tolerances), so don't assume "speed" constants are final.
2. **One Shuffleboard tab per subsystem**, named `"<Name> Subsystem Tab"`. `GenericEntry` fields created in the constructor via `tab.add(name, default).getEntry()`, written every loop in `periodic()`. Live PID tuning: entries seeded from gains, polled in `periodic()`, re-applied on change (see `ShooterSubsystem.java` periodic, "PID + FF Tuning" block — re-applies `Slot0Configs` via `getConfigurator().apply()`).
3. **Enum state machines** with actuation in `periodic()`: `IntakeSubsystem.IntakeSSTATE` (INTAKE_STATE/OUTTAKE_STATE/STOW_STATE), `HopperSubsystem.HOPPERSTATE` (RUN/STOW). Command factories mutate `desiredState` and `periodic()` drives the intake roller / hopper / kicker from it. Exception: the intake **slider** is driven directly inside the command sequences (`intakeSliderMotor.set(±0.5)` then stop), not by the state machine.
4. **Package layout**: mechanisms in `frc.robot.subsystems.misc`, helpers in `frc.robot.subsystems.utility` (`Sensors.java`, `LimelightHelpers.java` — LimelightHelpers is **vendored source**, not a vendordep). Swerve subsystem lives at `frc\robot\commands\CommandSwerveDrivetrain.java` — **nonstandard location** (a subsystem in the `commands` package); leave it there, import as `frc.robot.commands.CommandSwerveDrivetrain`.
5. **Tuner X-generated files**: `Constants\TunerConstants.java` and `commands\CommandSwerveDrivetrain.java` ("Generated by the 2026 Tuner X Swerve Project Generator"). Regenerate via Tuner X rather than hand-editing gains/offsets. `CommandSwerveDrivetrain` already contains hand additions (`configurePathPlanner()` with `AutoBuilder.configure`, `getAuton()`, `rotateToAngle()`; a Limelight MegaTag2 `addVisionMeasurement` block in `periodic()` that is **fully commented out**) — edit cautiously, never blind-overwrite.
6. Subsystems are constructed and bound in `frc\robot\RobotContainer.java` (single `CommandXboxController` on port 0; telemetry via `Telemetry.java` + `drivetrain.registerTelemetry`).

## Known-issues register (team has a brownout history — issue 1 is the prime suspect)

1. **No current limits on ANY mechanism motor.** Zero `CurrentLimitsConfigs` / `smartCurrentLimit` calls exist outside `TunerConstants.java` (grep-verified). Affects: 4× flywheel + kicker + intake-roller TalonFX, hood + slider + 2× hopper SparkMax. The **swerve IS limited** — steer 40 A stator limit (`TunerConstants.steerInitialConfigs`) and drive stator limit from `kSlipCurrent = Amps.of(120)` (Phoenix 26.1.0 `SwerveModule` bytecode copies `SwerveModuleConstants.SlipCurrent` into `CurrentLimitsConfigs.StatorCurrentLimit` and enables it — verified via javap on the vendored jar); do not claim the drivetrain is unlimited. Add limits to every motor you touch (snippets below).
2. **Broken stall detection** — `IntakeSubsystem.isIntakeSliderStall()` (`subsystems\misc\IntakeSubsystem.java`): returns `Math.abs(intakeSliderMotor.get()) < STALL_SPEED && intakeSliderMotor.get() > 0`. `.get()` is the **commanded duty cycle**, not measured current — the predicate is only true for commanded duty in (0, 0.05), so it can never fire during the ±0.5 / −0.25 slider commands (the `> 0` term excludes negatives; `|±0.5|` fails the magnitude term). `intakeCommand()`/`outtakeCommand()`/`stowCommand()` race `waitUntil(stall)` vs `waitSeconds(1)`, so the **1 s timeout silently does all the work**; `stowSliderCommand()` has **no timeout and will hang forever**. Fix with measured current + `Debouncer`, e.g. `intakeSliderMotor.getOutputCurrent()` (`public double getOutputCurrent()` — confirmed via javap on the vendored REVLib 2026.0.3 jar).
3. **Placeholder-zero constants** in `Constants\SubsystemConstants.java` — treat as "not yet tuned", never copy as real values: `ClimbSubsystemConstants` (every field 0, **including both CAN IDs**); `Vision.PP_MAX_VELOCITY/_ACCELERATION/_ANGULAR_VELOCITY/_ANGULAR_ACCELERATION` (all 0 — any PathPlanner constraints built from these won't move); `IntakeSubsystemConstants.INTAKE_SLIDER_kP/kI/kD` and `INTAKE/OUTTAKE/STOW_SLIDER_INCHES` (all 0); `ShooterSubsystemConstants.SHOOTER_LOW_SPEED`, `DISTANCE_SHORT`, `DISTANCE_FAR`, `SHOOTER_SPEED_kS`, `SHOOTER_SPEED_kA` (0).
4. **Vision shooting commands zero** — `ShooterSubsystem.generateShooterFlywheelVelocity()` and `generateAngle()` both `return 0` (placeholders). With `enableVision` true, `periodic()` feeds these into the flywheel/hood setpoints, so vision-based shooting silently does nothing. (Currently masked: `RobotContainer` constructs `new ShooterSubsystem(false, drivetrain)`.)
5. **Static mutable state in a constants class** — `ShooterSubsystemConstants.desiredVelReached/desiredAngleReached` are `public static boolean`, written each loop by `ShooterSubsystem.periodic()` and read by `HopperSubsystem.periodic()` (only `desiredVelReached` actually gates the kicker; `desiredAngleReached` is just displayed). Hidden cross-subsystem coupling with no ordering guarantee; replace with a `BooleanSupplier`/method on `ShooterSubsystem` when refactoring. Do not add new mutable statics to `SubsystemConstants`.
6. **Followers asserted once** — `ShooterSubsystem` constructor: `shooterB.setControl(new Follower(shooterA.getDeviceID(), MotorAlignmentValue.Aligned))` (C/D use `Opposed`). Per Phoenix 6 docs (https://v6.docs.ctr-electronics.com/en/stable/docs/api-reference/api-usage/control-requests.html) control requests auto-retransmit at a fixed `UpdateFreqHz` by default, so once-in-constructor works; only if `UpdateFreqHz` is set to 0 (one-shot) must `setControl` be re-called ≥ 20 Hz. Keep the default; don't zero the update freq on followers.
7. **Stub sensors** — `subsystems\utility\Sensors.java`: `getIndexSensorA()/B()` hardcode `return true` (`DigitalInput` imported, never constructed), so `HopperSubsystem` "fuel detected" is always true.
8. (Adjacent gotcha) `ShooterSubsystem.periodic()` "Physics Lab" block: when `enableComp == false` it force-overwrites `desired_Velocity = 0` / `desired_Angle = MIN_ANGLE` **every loop**, so `setAngleAndVelocityCommand()` has no lasting effect unless `enableComp` is true (right-trigger `enableLiveData(true)`).

## When generating NEW code for this robot

- **Follow** the constants convention (new nested class in `SubsystemConstants.java`, units in names/comments) and the one-Shuffleboard-tab-per-subsystem pattern.
- **Use `Commands` factories with proper requirements.** Existing `Commands.runOnce(() -> ...)` calls declare none — for new code pass the subsystem: `Commands.runOnce(() -> ..., subsystem)` or `subsystem.runOnce(...)`.
- **Prefer command composition** (`Commands.sequence/parallel/race`, `deadline`, `withTimeout`) over enum-in-`periodic()` state machines for new subsystems. Don't rewrite existing state machines unless asked.
- **Always add current limits.** Phoenix 6 v26 Follower signature is grounded in `ShooterSubsystem.java` (takes `MotorAlignmentValue`, **not** a boolean — API drifted from older Phoenix 6).

```java
// TalonFX (Kraken/Falcon) — Phoenix 6 v26. Field style matches the docs example:
// https://v6.docs.ctr-electronics.com/en/stable/docs/hardware-reference/talonfx/improving-performance-with-current-limits.html
// (all four fields confirmed as public double/boolean via javap on the vendored 26.1.0 jar;
//  builder style withStatorCurrentLimit(Amps.of(40)) also valid — see TunerConstants.java)
var limits = new CurrentLimitsConfigs();          // com.ctre.phoenix6.configs
limits.StatorCurrentLimit = 60;                   // A — caps torque/heat; size per mechanism
limits.StatorCurrentLimitEnable = true;
limits.SupplyCurrentLimit = 40;                   // A — caps battery draw (brownout protection, per docs page above)
limits.SupplyCurrentLimitEnable = true;
motor.getConfigurator().apply(limits);            // pattern grounded in ShooterSubsystem.java
```

```java
// SparkMax — REVLib 2026 config API (snippet matches the docs example):
// https://docs.revrobotics.com/revlib/spark/configuring-a-spark
SparkMaxConfig config = new SparkMaxConfig();     // com.revrobotics.spark.config
config.smartCurrentLimit(20);                     // A (int) — SparkMax default is 80 A; REV says adjust it for NEO 550
                                                  // (locked-rotor data: https://docs.revrobotics.com/brushless/neo/locked-rotor-testing)
                                                  // ~20 A (NEO 550) / ~40 A (NEO) is common community sizing, not a REV-prescribed number
spark.configure(config, ResetMode.kResetSafeParameters, PersistMode.kPersistParameters);
// configure(SparkBaseConfig, ResetMode, PersistMode) + smartCurrentLimit(int) confirmed via javap on REVLib 2026.0.3 jar
```

- Stall/jam detection: measured current, not commanded output — TalonFX `motor.getStatorCurrent().getValueAsDouble()` (`StatusSignal<Current> getStatorCurrent()` confirmed via javap on the Phoenix 26.1.0 jar; `.getValueAsDouble()` is the same pattern as `shooterA.getVelocity().getValueAsDouble()` in `ShooterSubsystem.java`) / SparkMax `getOutputCurrent()` (returns `double`, confirmed in the REVLib 2026.0.3 jar), wrapped in `edu.wpi.first.math.filter.Debouncer` (confirmed in wpimath 2026.2.1 jar), always with a timeout fallback.
- **Docs-version trap:** `codedocs.revrobotics.com` currently serves a newer Signal-based REVLib javadoc (`Signal<Double> getOutputCurrent()`, no `set()`/`get()`) that does **not** match the vendored REVLib 2026.0.3 — trust the project source and the cached jar, not that site.
